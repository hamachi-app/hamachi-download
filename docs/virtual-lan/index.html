Hamachi virtual LAN, explained

Peers behave like machines on one switch — without port forwarding or router changes.

The idea

A local network works because every machine can reach every other machine directly and has an address it can trust. Hamachi reproduces that over the internet: each machine in your network receives an address in the 25.x.x.x range, and the client moves packets between peers as if they shared a switch. Applications never learn that the peer is on another continent.

How the packets travel

  • Brokered connection. Peers find each other through LogMeIn's infrastructure, so no inbound port has to be open on either side.
  • Direct peer-to-peer. When both NATs allow it, traffic moves directly between the machines and the relay is not in the path.
  • Relay. When a direct path cannot be established, traffic is relayed. It works, but latency and throughput are worse — a relayed link is the usual explanation for "Hamachi feels slow".

What actually works over it

  • LAN games. Titles that only browse the local subnet see the Hamachi network as one.
  • SMB file sharing. \\25.x.x.x\share behaves like any UNC path.
  • Remote Desktop. RDP to a peer's Hamachi address.
  • IP cameras and lab gear. Devices with no public IP and no way to configure one.
  • Gateway mode. One peer routes a whole subnet, so you reach machines that have no Hamachi client at all. This is a paid-plan feature.

What it is not

It is not a privacy VPN. Traffic between peers is not routed through an exit node in another country and does not change your public IP. It is a private network between machines you invited, not a tunnel for browsing.

Limits worth knowing

The free tier allows up to 5 devices in a network. Larger networks and gateway features require a subscription. Addresses are assigned by the client and are stable for a given machine while it stays in the network.
